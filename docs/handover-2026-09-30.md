## 3. The system, in brief

A small decoder, LFM2.5-350M, with a latent knowledge base (KB).

- **Model.** It is the BGKit S2 checkpoint at `/workspace/checkpoints/bgkit2_step19999_...` inside the container.
- **Memory tools.** `memory_search()` and `memory_write()` take no arguments.
  - The query is the model's hidden state at the call.
  - A write is a latent span the model generates in place, in a single pass.
- **KB entries.** Each entry is a compressed latent span stored in four spaces at equal information: A, B, C and D are 256, 512, 1024 and 2048 wide at 1, ½, ¼ and ⅛ of the positions.
  - Codecs (trained in the stage called K1) map writer spans into the spaces.
  - A recombiner R turns retrieved entries into a span the decoder reads.
- **Extreme sparsity.** Reads are frequent, and each touches a few entries.
- **Superposition (designed and built, currently parked).** Stored rows are outputs of write-side aggregators over fields of inputs, with overlapping fields and key-dependent shares. The plan has a long read-side phase with free rows, then a write fit to the rows. It is parked until retrieval and content use work on plain (leaf) banks.

**Stage names used in code and docs:**

| Stage | What it trains |
|---|---|
| B2–B4 | The writer. B4 includes: protocol SFT so the model emits memory calls; the soft output port; writes; slot spans in write prefixes. |
| K1 | Codecs and recombiner (autoencoding through the spaces). |
| K2 | Retrieval-only training of query and key heads. |
| L1a | Content use through reads, with task loss. Items trained in place. |
| L1b | Gradients back to the writer and codecs. |
| L2 | Producers reproduce the adapted entries. |
| B9 | Learning by experience: read and write over rounds. |

## 4. The main findings, 28–30 September

1. **Reads on SQL carried no content.** On plain text-to-SQL, R learned a content-free format prompt: shuffled reads helped as much as the right ones. The fix was to change the tasks.
2. **Probe tasks.** The move was to high-redundancy, high-target-entropy tasks with *diverse* copies:
   - verbatim recall of Wikipedia text from overlapping windows;
   - parallel Bible translations, with the target version never stored;
   - citance recall: a paper's abstract from other papers' citation contexts;
   - r6 QA passages;
   - a synthetic people world as a redundancy knob.

   SQL schema aliasing exists as code, but no corpora were built; SQL is deprioritized.
3. **Retrieval losses.**
   - Redundant copies of a slot count as positives (`alternatives`), never negatives.
   - Same-document near-duplicates are `neutral`: neither positive nor negative.
4. **Content warm start.** `--gold-reads` lets a share of episodes read their correct items, so R learns to use content before retrieval works.
5. **Why retrieval failed, and the fix.**
   - The query taken at layer 8 at the call token was degenerate: effective rank about 2.5, and nearly identical across episodes.
   - LFM2.5 has full attention only at layers 2, 5, 8, 10, 12 and 14; the other layers are short local convolutions. Nothing gathers the request at the call token.
   - **Fix (the "arm f" recipe):**
     - the query is the call-token state at the **final layer** (`--query-layer 16`);
     - **LoRA 16** on the reader's own copy of the decoder layers (`--decoder-train-below query --decoder-lora 16 --decoder-lr 5e-4`), with parent KL (`--decoder-replay-kl 1.0`);
     - **centered alignment** of both key towers to a text-embedding teacher (`--key-align-weight 10 --key-align-center`);
     - teacher KL (`--key-teacher DIR --key-teacher-weight 1`).

     The teacher is Qwen3-Embedding-0.6B, cached. It is used only as supervision during training; inference stays latent.
   - **Tried and dropped:**
     - the prefix pool, which is not conditioned on the call;
     - a query-former module, which collapsed in every variant;
     - soft superposed reads, which train the query but blur the reads and run four times slower.
6. **Query formulation is separate from answering.** In L1a, `--decoder-query-only` means the trained layers only form the query, and the parent decoder reads and answers. Otherwise the model memorizes training answers.
7. **K2 data.**
   - Inverse-cloze corpora, where the cue is a sentence and the target is its record plus copies.
   - `l1 subkb`: small KBs with random, teacher-mined or mixed distractors.
   - `--hard-negatives` / `--dump-hits`.
8. **K1 space balance.** A carries most information. Rebalancing (single-space weight 1.0, A dropout 0.75) lifted C and D from 0.44/0.28 to 0.48/0.32, then K1 plateaued and was stopped. D is treated as a coarse index space for now. Remedies if needed: more capacity for C and D, or distillation from A.

## 8. Operating rules (learned the hard way)

- **Memory.** CPU and GPU share 121 GB on the DGX Spark, so a job's cuda fraction × 121 GB is real host memory.
  - Before any GPU launch, add up every running job, every armed waiter script that may auto-launch, and every agent that may start GPU work.
  - Keep **at least 25 GB available** after all of them.
  - earlyoom kills the Claude session first below 10%. It happened on 29 September at 03:34.
- **Disk.** Keep **at least 40 GB free** on `/`; it is a 916 GB root shared with other projects. The root filled once, and B4 and K1 crashed mid-save.
  - Training writes go to the NVMe (`/runs`).
  - Move finished runs asynchronously to `/mnt/external/sdkb-archive/runs/cold-<date>/`. Don't delete them, except for pure scratch copies.
  - Some old files are owned by host root with mode 0600. The `sdkb-causal-pilot` container (host root) can read and move them; `sdkb-bgkit` cannot.
- **Killing processes.** List pids first (`ps -eo pid,args | grep "[p]attern"`; inside the container, read `/proc/<pid>/cmdline`), then kill the explicit pids. Never use `pkill -f` or `pgrep -f` with a pattern that appears in the same command line.
- **Log paths.** A host script's log redirect must use host paths (`/home/werg/...`), not `/runs`. One build died silently because of that.
- **Merging agent branches.** The usual conflicts are additive, in `docs/bgkit-restart-plan.md` and `docs/knowledge-base-stack.md`: keep both sides. Then run the full suite in the container, run ruff on the host, and push.
- **Agents.** Always give each agent:
  - a hard GPU budget (one process, cuda fraction ≤ 0.08);
  - a disk check before writing anything over 1 GB;
  - the no-`pkill -f` rule;
  - "commit on your branch, do not merge".

## 10. Useful command patterns

The K2 run with the working recipe (copy the banks first; training modifies a KB in place):

```
python scripts/train.py l1 train --checkpoint <bgkit2 ckpt> --reader-state /runs/bgkit-restart/b3-writer-step11500.pt \
  --cuda-fraction 0.08 --transcripts <memory corpus> --limit N --eval-limit M --batch-size 8 --eval-items 64 \
  --banks <banks copy> --output <out> --steps 3000 --eval-every 250 --retrieval-only --lr 1e-3 --retrieval-weight 1.0 \
  --key-teacher <teacher-keys dir> --key-teacher-weight 1.0 --key-align-weight 10 --key-align-center \
  --query-layer 16 --decoder-train-below query --decoder-lora 16 --decoder-lr 5e-4 --decoder-replay-kl 1.0 --decoder-checkpoint
```

- **L1a:** start from K2 with `--init-reader <reader.pt> --init-reader-full`, drop `--retrieval-only`, and add:

  ```
  --decoder-query-only --decoder-lr 1e-4 --item-lr 3e-3 --gold-reads 0.5 --gold-anneal 1500 --contrast-weight 1 --contrast-margin 0.5 --null-prefix 4
  ```
- **Banks:** `l1 build --transcripts ... --limit N --eval-limit M --codecs k1-stack-step15500.pt --span-cache <existing spans dir> --output <banks>`. Writer throughput is about 6 records per second.
- **Teacher cache:** `l1 teacher-keys --banks <banks> --output <dir>`. It uses the cached Qwen3-Embedding with `HF_HUB_OFFLINE=1`, about 15 minutes for 72k records.
- **Evaluation fields** in the `"eval"` lines:
  - `nll` arms: `noctx`, `full`, `retrieved`, `shuffled`, `gold`, `gold_shuffled`;
  - `content_nats` (retrieved or gold minus shuffled);
  - `reads.recall_<space>` (search recall) and `recall_read_<space>` (among the items read).

  Training-line recall includes gold-read episodes, so it is not a validation measure.
